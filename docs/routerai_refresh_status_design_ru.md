# Наблюдаемое автоматическое обновление внешних данных: RouterAI как эталонный пример

## 1. Назначение документа

Этот документ фиксирует не только реализацию RouterAI updater, но и инженерский шаблон, который можно воспроизвести для другого внешнего каталога, справочника, списка версий, тарифов, совместимости или иных периодически обновляемых данных.

Документ сохраняет цели, исходные проблемы, принятые решения, границы владения, failure model и пользовательскую доставку состояния. Это нужно, чтобы следующий механизм не пришлось проектировать заново по истории диалогов.

Краткая операционная инструкция RouterAI находится в `docs/routerai_catalog_updates_ru.md`.

## 2. Какие проблемы решает архитектура

Наивная схема `API → script → commit` не отвечает на следующие вопросы:

- что является ручным source of truth, а что производным состоянием;
- как не дать человеку или агенту незаметно исправить generated data вручную;
- как при этом сохранить возможность менять ручную policy;
- как автоматическая ветка переживает движение `main`;
- что делать при настоящем конфликте;
- как отличить «проверили источник, изменений нет» от «давно не проверяли»;
- как сохранить last-known-good после новой ошибки;
- как отличить candidate от published state;
- как сообщить конечному пользователю о деградации именно перед использованием данных;
- как не превратить временную недоступность status channel в отказ основного продукта;
- как хранить диагностику, не публикуя secrets и полный stderr.

Цель — сделать доставку внешних данных воспроизводимой, наблюдаемой и fail-closed там, где состояние неоднозначно.

## 3. Разделение источников истины

Для RouterAI:

```text
templates/routerai_model_policy.json      ручная политика
RouterAI GET /api/v1/models               внешний объективный источник
                    │
                    ▼
                 генератор
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
config_data.json   opencode     generated snapshot
-> models          template     RouterAI
```

Человек/агент определяет выбор моделей, роли и описания только через policy. Внешние цены и каталог принадлежат полному refresh. Представления в config/template производны от policy + snapshot.

## 4. Два разных вида генерации

### 4.1. Полный внешний refresh

```text
gh workflow run routerai_catalog.yml --repo dilukhin/agent-toolchain --ref main
```

Он обращается к RouterAI, может изменить snapshot и создаёт/обновляет автоматический PR.

### 4.2. Офлайновая пересборка после изменения ручной policy

```text
python3 scripts/update_routerai_catalog.py --sync-generated
```

Она принципиально не обращается в сеть и не меняет `templates/routerai_catalog.generated.json`. Из уже сохранённого snapshot и новой policy она пересобирает только производные config/template области.

Это устраняет важную взаимоблокировку: если CI одновременно запрещает ручную правку generated sections и требует их соответствия policy, policy должна иметь штатный путь регенерации без присвоения обычному PR права менять внешний snapshot.

## 5. Воспроизводимость как критерий разрешения

CI не пытается надёжно определить «кто автор строки». Такой security boundary ненадёжен для bot/user/agent.

Вместо этого используется проверяемое свойство:

> Обычный PR может содержать изменение производной области только тогда, когда результат точно воспроизводится штатным офлайновым генератором из разрешённых источников истины.

Поэтому:

- policy изменилась + `--sync-generated` выполнен → допустимо;
- policy изменилась, generated state не пересобран → CI падает;
- generated state изменён без policy → CI падает;
- generated state изменён произвольно вместе с policy → CI падает, если результат не воспроизводится;
- внешний snapshot изменён обычным PR → CI падает всегда.

Это переносимый принцип для любого generated-state.

## 6. `_managed_notice`

В форматах, где неизвестное служебное поле безопасно, generated resource содержит читаемый `_managed_notice`.

Он должен отвечать минимум на вопросы:

1. можно ли редактировать этот ресурс вручную;
2. какой механизм им владеет;
3. где находится ручной source of truth;
4. как пересобрать производные данные;
5. как запустить полный внешний refresh;
6. где прочитать архитектурные причины.

Для RouterAI `_managed_notice` рекламирует именно этот документ.

Предупреждение помогает человеку/агенту, но не является технической защитой: защиту обеспечивает CI.

## 7. Почему одного PR недостаточно для статуса

PR остаётся удобным review gate, но не может быть единственным status channel:

- успешная проверка без изменения данных не создаёт commit;
- workflow может упасть раньше шага PR;
- предыдущий PR может быть уже merged/closed;
- клиенту не следует разбирать PR как машинный API;
- статус должен хранить предыдущий успех после новой ошибки.

Поэтому catalog candidate и updater status разделены.

## 8. Служебные ветки

### `automation/routerai-catalog`

Содержит кандидат производных данных относительно `main`, проходит PR review и Windows/Linux validation.

### `automation/routerai-status`

Содержит только:

```text
routerai-refresh-status.json
```

Ветка полностью automation-owned. Неизвестные дополнительные файлы не усыновляются и не удаляются автоматически. Status JSON также содержит `_managed_notice` с назначением ветки, ссылкой на этот документ и командой полного ручного refresh.

Git-история этой ветки служит журналом прошлых состояний; бесконечный `history[]` в JSON не нужен.

## 9. Модель состояния

Нужно различать минимум четыре сущности.

### `published`

Что фактически находится в `main`: время наблюдения snapshot и SHA публикации.

### `last_successful_check`

Когда внешний источник последний раз успешно получен и структурно принят, даже если данные не изменились.

### `last_attempt`

Последняя попытка независимо от результата: время, trigger, phase, status и санитизированная ошибка.

### `candidate`

Более новые данные, ещё не ставшие published, с PR/branch SHA и состоянием validation.

Ошибка новой попытки обновляет `last_attempt`, но не стирает `last_successful_check` и `published`.

## 10. Этапы и ошибки

Нельзя описывать pipeline одним `success`.

Типичные фазы RouterAI:

```text
sync-main
fetch-routerai
regressions
publish-candidate
pull-request
full-validation
complete
```

Разный этап означает разную причину и рекомендацию. Полный stderr остаётся в Actions; долговечный status получает только безопасный код/summary/advice.

## 11. Движение `main` и конфликты

`automation/routerai-catalog` перед refresh подтягивает актуальный `main`. Обычные независимые изменения должны объединяться автоматически.

Если Git не может безопасно объединить состояние, workflow не выбирает `ours/theirs`. Он останавливается, а status фиксирует `phase = sync-main`.

Особенно конфликт automation-owned области означает потенциальное нарушение ownership contract, миграцию или обход CI и требует review.

## 12. CI ownership gate

`.github/workflows/routerai_owned_diff.yml` запускает semantic guard на реальном PR.

Guard сравнивает base/head не по всему `config_data.json`, а по принадлежащим RouterAI областям. Независимые разделы файла остаются редактируемыми.

Для обычного PR внешний snapshot immutable. Производные config/template должны быть воспроизводимы из head policy + неизменного snapshot.

Служебная `automation/routerai-catalog` имеет узкое исключение, поскольку именно она владеет полным внешним refresh.

## 13. Клиентская доставка состояния

Пользователь должен узнать о качестве данных непосредственно перед тем, как начинает получать от них пользу. Для RouterAI это запуск OpenCode/Codex.

Запускатор:

1. читает локальный status cache;
2. при необходимости best-effort обновляет его;
3. показывает короткое русское сообщение;
4. всегда продолжает запуск, если проблема относится только к status/ценам.

Пример нормы:

```text
RouterAI: цены актуальны, каталог проверен 6 ч. назад.
```

Пример деградации:

```text
ВНИМАНИЕ: последняя попытка обновить цены RouterAI завершилась ошибкой.
Последняя успешная проверка была 1 дн. назад.
Используются последние опубликованные цены; запуск продолжается.
```

## 14. `unknown != stale`

Если GitHub/status сейчас недоступен, доказано только отсутствие свежей информации о состоянии. Нельзя превращать это в утверждение, что сами цены устарели.

Правильная модель:

```text
remote status недоступен
→ использовать локальный cache
→ сообщить возраст cache при необходимости
→ не блокировать основной продукт
```

## 15. Candidate, published и installed — разные состояния

Полезно различать:

```text
внешний источник
→ candidate в PR
→ published в main
→ installed у пользователя
```

Отсюда разные рекомендации:

- candidate существует → ждать review/merge;
- published новее installed → `toolchainctl update --apply`;
- last attempt failed, но last successful check свежий → данные свежие, updater деградирован;
- долго нет success → заметное предупреждение об устаревании подтверждения.

## 16. Что публиковать при ошибке

В долговечный status/PR разрешены только:

- phase;
- error code;
- короткое безопасное summary;
- рекомендация;
- ссылка/идентификатор Actions run при необходимости.

Нельзя автоматически копировать полный stderr, headers, tokens, локальные пути или большие tracebacks.

## 17. Как воспроизвести механизм для другой цели

Для нового внешнего источника последовательно определить:

1. **Ручной source of truth.** Что решает человек, а не API.
2. **Внешний snapshot.** Какой объективный payload сохраняется и кто им владеет.
3. **Производные области.** Какие файлы/JSON paths вычисляются из policy + snapshot.
4. **Полный refresh.** Отдельный workflow, который имеет право менять snapshot.
5. **Офлайновую пересборку.** Режим, меняющий только derived state после ручной policy.
6. **Verifier.** Доказательство, что derived state воспроизводится без сети.
7. **PR guard.** Запрет snapshot mutation обычными PR и разрешение только воспроизводимых derived changes.
8. **Managed notice.** Краткое предупреждение + команды + ссылка на архитектурный документ.
9. **Status channel.** `published`, `last_successful_check`, `last_attempt`, `candidate`.
10. **Fail-closed conflict policy.** Не угадывать разрешение неоднозначного ownership.
11. **Клиентскую точку показа.** Где пользователь действительно увидит актуальность до использования данных.
12. **Best-effort cache.** Наблюдаемость не должна становиться обязательной runtime-зависимостью без отдельного требования.
13. **Санитизацию ошибок.** Короткий публичный статус, полный журнал отдельно.
14. **Тестовые сценарии.** Success/no-change, внешняя ошибка, конфликт, invalid payload, candidate pending/failed/success, published newer than installed, недоступный status.

Если эти пункты нельзя однозначно определить, механизм ещё не готов к автоматической mutation.

## 18. Антипаттерны

Не следует:

- писать внешний API прямо в `main` без review gate;
- считать PR единственным источником health/status;
- хранить только последний failure и терять last-known-good;
- разрешать policy, но не давать способ безопасно пересобрать derived state;
- разрешать обычному PR менять внешний snapshot под видом синхронизации policy;
- определять разрешение только по имени автора commit;
- автоматически выбирать `ours/theirs` при смысловом конфликте;
- блокировать основной runtime только потому, что advisory/status недоступен;
- копировать полный stderr в status JSON.

## 19. Критерий готовности шаблона

Механизм считается зрелым, когда одновременно выполняются свойства:

- **воспроизводимость** — derived state можно доказать офлайн;
- **защищённость** — произвольная ручная mutation generated area не получает зелёный CI;
- **изменяемость policy** — ручной source of truth можно менять через отдельную безопасную пересборку;
- **наблюдаемость** — известны последняя попытка и последний успех;
- **доставка состояния** — конечный пользователь получает понятное сообщение в правильной точке использования;
- **отказоустойчивость** — сбой внешнего API/status не уничтожает last-known-good и не ломает основной продукт;
- **переносимость решения** — причины и шаблон задокументированы так, чтобы механизм можно было применить к другой цели без восстановления истории обсуждений.
