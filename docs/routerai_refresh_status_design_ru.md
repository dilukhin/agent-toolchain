# Наблюдаемое автоматическое обновление внешних данных: RouterAI как эталонный пример

## 1. Назначение

Этот документ описывает не только конкретный механизм обновления цен RouterAI, но и общий инженерный шаблон для автоматического получения внешних данных, подготовки производного состояния, безопасной публикации и доставки информации о качестве этого процесса конечному пользователю.

RouterAI здесь является первым практическим применением шаблона.

Документ должен помогать ответить на два разных вопроса:

1. как сейчас устроено обновление RouterAI в `agent-toolchain`;
2. как воспроизвести ту же архитектуру для другого внешнего каталога, справочника, метаданных, списка версий или иной автоматически поддерживаемой информации.

Операционные команды и краткое описание RouterAI находятся также в `docs/routerai_catalog_updates_ru.md`.

## 2. Исходная проблема

Простая схема вида

```text
внешний API
→ скрипт
→ изменить файл
→ commit
```

недостаточна для production-механизма.

Она не отвечает на важные вопросы:

- что является ручным источником истины, а что производным состоянием;
- что произойдёт, если человек или агент вручную исправит производный файл;
- как автоматическая ветка переживает движение `main`;
- как обнаружить и безопасно остановить настоящий конфликт;
- как понять, что внешний источник успешно проверялся, даже когда данные не менялись;
- как сохранить последнюю успешную проверку после новой ошибки;
- как отличить «внешние данные свежие» от «новый кандидат существует, но ещё не опубликован»;
- как конечный пользователь узнает о деградации до того, как начнёт пользоваться зависимыми от данных инструментами;
- как не превращать временную недоступность сети в отказ основного продукта;
- как хранить диагностику без публикации секретов и больших журналов.

Цель архитектуры — закрыть эти вопросы системно.

## 3. Основные принципы

### 3.1. Ручное и производное состояние разделены

Для RouterAI:

```text
templates/routerai_model_policy.json
    ручная политика

RouterAI GET /api/v1/models
    внешний объективный источник

оба источника
    ↓
генератор
    ↓
config_data.json -> models
templates/opencode.jsonc -> provider.routerai.models
templates/routerai_catalog.generated.json
```

Ручная политика определяет выбор моделей, роли и описания.

Цены, актуальный внешний каталог и производные представления принадлежат генератору.

### 3.2. Производный ресурс явно объявляет владельца

В JSON, где это безопасно для потребителей, записывается `_managed_notice`.

Предупреждение должно отвечать минимум на четыре вопроса:

- нельзя ли редактировать этот участок вручную;
- кто им управляет;
- где находится ручной источник истины;
- где прочитать подробности и как штатно запустить обновление.

Каноническая команда полного ручного запуска RouterAI:

```text
gh workflow run routerai_catalog.yml --repo dilukhin/agent-toolchain --ref main
```

### 3.3. Предупреждение не является защитой

`_managed_notice` нужен человеку и агенту, но техническое правило обеспечивает CI.

Обычный PR не должен иметь возможность изменить automation-owned область и остаться зелёным.

### 3.4. Производное состояние должно быть воспроизводимо офлайн

Для RouterAI существует отдельная проверка:

```text
python3 scripts/update_routerai_catalog.py --verify-generated
```

Она не обращается к RouterAI.

Проверка берёт сохранённый каталог и ручную policy и доказывает, что производные области репозитория соответствуют им.

Это другой вопрос, чем:

```text
изменился ли внешний RouterAI прямо сейчас?
```

Поэтому сетевое обновление и офлайновая проверка не смешиваются.

### 3.5. Неизвестно не означает устарело

Если клиент временно не может получить удалённый статус, это означает только отсутствие новой информации.

Нельзя делать вывод:

```text
GitHub недоступен
→ цены устарели
```

Допустимый вывод:

```text
GitHub недоступен
→ новый статус сейчас проверить нельзя
→ использовать последний локально закэшированный статус
```

### 3.6. Ошибка наблюдаемости не блокирует основной продукт

Информация о ценах вспомогательная.

Ошибка RouterAI, GitHub или статусного канала не должна блокировать запуск OpenCode/Codex.

Запускатор показывает предупреждение и продолжает работу.

## 4. Почему одного pull request недостаточно

PR полезен как:

- место review;
- человеко-читаемая сводка кандидата;
- шлюз перед `main`;
- журнал значимых событий.

Но PR не является достаточным источником состояния обновлятора.

Причины:

1. успешная проверка внешнего API без изменения данных не обязана создавать новый commit;
2. workflow может упасть до шага создания/обновления PR;
3. предыдущий PR может быть уже merged/closed;
4. конечному клиенту неудобно и ненадёжно разбирать GitHub PR как машинный API;
5. статус должен сохранять последнюю успешную попытку независимо от текущей ошибки.

Поэтому введён отдельный машинно-читаемый канал состояния.

## 5. Две служебные ветки

### 5.1. `automation/routerai-catalog`

Назначение:

- кандидат производных данных;
- синхронизация с актуальным `main`;
- PR в `main`;
- полная Windows/Linux проверка.

Эта ветка может иметь обычную Git-историю относительно `main`.

### 5.2. `automation/routerai-status`

Назначение:

- только текущее машинно-читаемое состояние обновлятора;
- сохранение статуса даже при ошибке catalog-ветки;
- источник для клиентского кэша и запускаторов.

Разрешённый payload ветки:

```text
routerai-refresh-status.json
```

Любые дополнительные файлы считаются нарушением ownership и не должны автоматически усыновляться или удаляться.

Сам JSON содержит `_managed_notice` с указанием этого документа и команды ручного запуска.

История коммитов ветки является журналом прошлых состояний; бесконечный массив истории внутри JSON не нужен.

## 6. Модель состояния

Нужно различать минимум следующие сущности.

### 6.1. `published`

Что реально опубликовано в `main`.

Пример:

```json
{
  "published": {
    "catalog_observed_at": "2026-08-28T15:22:09Z",
    "main_sha": "..."
  }
}
```

Это не обязательно время последней проверки внешнего источника. Это возраст фактически опубликованных данных.

### 6.2. `last_successful_check`

Когда внешний источник последний раз успешно получен и структурно принят.

Пример:

```json
{
  "last_successful_check": {
    "at": "2026-08-29T03:18:12Z",
    "catalog_changed": false
  }
}
```

Поле обновляется даже когда цены не изменились.

Именно оно отвечает на вопрос:

> когда мы последний раз действительно проверяли RouterAI и получили корректный ответ?

### 6.3. `last_attempt`

Последняя попытка независимо от результата.

Пример ошибки:

```json
{
  "last_attempt": {
    "at": "2026-08-30T03:18:14Z",
    "trigger": "schedule",
    "status": "failed",
    "phase": "fetch-routerai",
    "error": {
      "code": "routerai-refresh",
      "summary": "Не удалось получить или обработать актуальный каталог RouterAI.",
      "advice": "Повторите штатное обновление..."
    }
  }
}
```

Ошибка не стирает `last_successful_check`.

### 6.4. `candidate`

Более новые данные, ещё не ставшие published-state.

Пример:

```json
{
  "candidate": {
    "catalog_observed_at": "2026-08-30T03:17:54Z",
    "branch_sha": "...",
    "pr_number": 31,
    "validation": "success"
  }
}
```

Допустимые состояния проверки:

```text
pending
success
failed
```

Если кандидата нет:

```json
{
  "candidate": null
}
```

## 7. Почему последняя успешная проверка сохраняется после ошибки

Рассмотрим последовательность:

```text
29 августа
RouterAI успешно проверен

30 августа
RouterAI timeout
```

Неправильное состояние:

```text
status = failed
```

Оно теряет полезную информацию.

Правильное состояние:

```text
last_successful_check = 29 августа
last_attempt = failed at 30 августа
```

Тогда пользователь понимает одновременно:

- данные подтверждались недавно;
- обновлятор сейчас деградировал;
- используются последние известные корректные данные.

Эта модель переносима на любые периодически обновляемые внешние данные.

## 8. Этапы попытки

Не следует обозначать весь pipeline одним `success`.

Типичная цепочка:

```text
получить внешний источник
→ нормализовать/сгенерировать
→ локальные регрессии
→ опубликовать candidate branch
→ создать/обновить PR
→ выполнить полную платформенную проверку
→ merge
```

Ошибка каждого этапа имеет разный смысл и разную рекомендацию.

Для RouterAI используются понятные фазы, например:

```text
sync-main
fetch-routerai
regressions
publish-candidate
pull-request
full-validation
complete
```

В status-файл попадает короткая безопасная диагностика.

Полный stderr/trace остаётся в GitHub Actions.

## 9. Fail-closed при конфликте

Если `automation/routerai-catalog` не может безопасно слить актуальный `main`, автоматизация не выбирает автоматически `ours` или `theirs`.

Она останавливается и фиксирует ошибку:

```text
phase = sync-main
```

Особенно это важно для automation-owned областей: конфликт может означать, что:

- CI guard был обойдён;
- изменился ownership contract;
- идёт осознанная миграция;
- кто-то вручную редактировал производный ресурс.

Неоднозначность требует review.

## 10. PR ownership gate

Обычные ветки разработки могут изменять независимые части `config_data.json`.

Они не могут непосредственно изменять:

```text
config_data.json -> models
templates/opencode.jsonc -> provider.routerai.models
templates/routerai_catalog.generated.json -> весь файл
```

Исключение — служебная ветка `automation/routerai-catalog`.

Проверка выполняется по семантическим JSON-областям, а не просто по имени файла.

Это позволяет одновременно:

- защищать generated state;
- не блокировать обычные изменения других частей `config_data.json`.

## 11. Пользовательский status channel

Удалённый источник:

```text
automation/routerai-status/routerai-refresh-status.json
```

На клиенте он загружается best-effort и сохраняется в локальном кэше.

Запускатор не должен делать обязательный сетевой запрос при каждом старте.

Модель:

```text
если кэш свежий
    использовать его

если TTL истёк
    короткая попытка обновить

если сеть недоступна
    использовать последний кэш
    сообщить, что удалённое состояние сейчас проверить нельзя
```

Для RouterAI исходный TTL — 6 часов.

## 12. Пользовательский интерфейс перед запуском

Нормальное состояние:

```text
RouterAI: цены актуальны, каталог проверен 6 ч. назад.
```

Последняя попытка упала:

```text
ВНИМАНИЕ: последняя попытка обновить цены RouterAI завершилась ошибкой;
последняя успешная проверка была 1 дн. назад.
Причина последней ошибки: RouterAI не ответил за отведённое время.
Используются последние опубликованные цены; запуск продолжается.
```

Есть проверенный кандидат:

```text
Обнаружены более новые цены RouterAI; кандидат проверен и ожидает слияния PR #31.
```

`main` свежее установленного клиента:

```text
В main уже опубликованы более новые цены.
Обновить установленный toolchain: toolchainctl update --apply
```

Основной CLI всё равно запускается.

## 13. Возраст данных и деградация — разные измерения

Нужно отдельно учитывать:

- возраст последней успешной проверки;
- результат последней попытки.

Пример:

```text
последний успех 4 часа назад
последняя попытка час назад упала
```

означает свежие данные, но деградировавший updater.

Пример:

```text
последний успех 5 дней назад
последняя попытка час назад упала
```

означает и деградацию, и реальное старение подтверждённости данных.

Для RouterAI исходная политика:

```text
до 36 часов       актуально
36–72 часа        устаревает
более 72 часов    устарело
```

Эти пороги должны быть централизованными константами и тестироваться.

## 14. Санитизация ошибок

В status branch и PR запрещено автоматически копировать полный stderr или traceback.

Допустимый набор:

```text
phase
error code
короткое безопасное описание
время
рекомендация
при необходимости идентификатор workflow run
```

Полная техническая диагностика остаётся в Actions logs.

Причина:

- исключить секреты/authorization headers;
- не публиковать приватные пути;
- не раздувать постоянный status;
- не переносить потенциально непроверенный внешний payload в пользовательский интерфейс.

## 15. Операционные команды RouterAI

Полный штатный ручной запуск:

```text
gh workflow run routerai_catalog.yml --repo dilukhin/agent-toolchain --ref main
```

Локальная разработческая регенерация checkout:

```text
python3 scripts/update_routerai_catalog.py --write
```

Это разные операции.

Офлайновая проверка производного состояния:

```text
python3 scripts/update_routerai_catalog.py --verify-generated
```

Получение уже опубликованного `main` на пользовательской машине:

```text
toolchainctl update --apply
```

## 16. Сценарии

### 16.1. Ежедневная проверка, изменений нет

```text
03:17 workflow start
03:18 RouterAI успешно ответил
данные не изменились
```

Результат:

```text
published остаётся прежним
last_successful_check обновляется
last_attempt = success
candidate не обязан меняться
```

Это одна из основных причин существования status branch.

### 16.2. RouterAI недоступен

```text
last_successful_check сохраняется
last_attempt = failed
published сохраняется
```

Клиент продолжает использовать последние опубликованные цены.

### 16.3. Новые цены ожидают merge

```text
новый RouterAI catalog
→ candidate
→ PR
→ Windows/Linux validation success
→ ещё не merged
```

Пользователь получает информацию о наличии более свежего кандидата, но продолжает видеть published-state.

### 16.4. Новый каталог уже в main, клиент не обновлён

Status показывает published-state новее локального `observed_at`.

Рекомендация:

```text
toolchainctl update --apply
```

### 16.5. Конфликт с main

Catalog branch не удаётся синхронизировать.

Автоматизация:

- не применяет эвристический merge;
- пишет failure status в независимую status branch;
- сохраняет предыдущий successful check;
- даёт рекомендацию разобрать конфликт.

## 17. Как воспроизвести механизм для другой цели

Для нового источника внешних данных не следует копировать только workflow.

Нужно последовательно определить следующие контракты.

### Шаг 1. Определить ручной source of truth

Ответить:

- что выбирает человек;
- что приходит извне;
- что является производным.

### Шаг 2. Объявить generated ownership

Для каждого производного ресурса указать:

- файл;
- JSON path или весь файл;
- генератор;
- ручной альтернативный источник;
- документацию;
- штатную команду запуска.

### Шаг 3. Добавить человеко-читаемый notice

Если формат допускает — `_managed_notice`.

Если нет — ближайший безопасный документ/config metadata.

### Шаг 4. Добавить offline reproducibility check

Проверка не должна зависеть от внешней сети.

Она доказывает:

```text
сохранённый внешний snapshot
+
ручная policy
=
текущий generated state
```

### Шаг 5. Добавить PR ownership gate

Обычный PR не должен напрямую менять generated area.

### Шаг 6. Разделить candidate и status

Candidate branch хранит новые данные.

Status branch хранит здоровье updater.

Они не должны иметь одинаковую failure domain.

### Шаг 7. Определить status schema

Минимум:

```text
published
last_successful_check
last_attempt
candidate
```

### Шаг 8. Сделать status writer fail-safe

Запись статуса должна выполняться после основной попытки даже при её failure.

### Шаг 9. Определить пользовательскую точку показа

Статус ценен только если его увидят до использования зависимой функции.

Для RouterAI это запуск OpenCode/Codex.

Для другого механизма это может быть:

- запуск компилятора;
- deployment;
- открытие отчёта;
- выполнение команды, использующей справочник;
- health/check команды.

### Шаг 10. Не делать advisory новой обязательной зависимостью

Если статус вспомогательный, его недоступность не должна ломать основную функцию.

### Шаг 11. Санитизировать persistent diagnostics

Никогда не публиковать raw error автоматически без отдельной политики.

### Шаг 12. Протестировать сбои

Минимум:

- источник недоступен;
- источник вернул malformed data;
- данных нет;
- данных нет новых;
- candidate изменился;
- candidate validation failed;
- status branch отсутствует;
- status branch содержит чужие файлы;
- сеть клиента недоступна;
- локальный кэш устарел;
- main новее клиента.

## 18. Антипаттерны

Не использовать:

```text
последний workflow зелёный → всё актуально
```

Причина: workflow мог ничего не знать о published-state или последующем validation.

Не использовать:

```text
один timestamp last_update
```

Причина: он не различает успешную проверку, изменение данных, публикацию и ошибку.

Не использовать:

```text
ошибка → стереть прошлый success
```

Причина: теряется last-known-good.

Не использовать:

```text
PR body как единственный API состояния
```

Причина: PR может отсутствовать или не обновиться.

Не использовать:

```text
если status не загрузился → блокировать продукт
```

если status не является обязательной runtime dependency.

Не использовать:

```text
ours/theirs для generated conflict
```

без доказанного ownership и отдельного контракта разрешения.

## 19. Критерии готовности такого механизма

Механизм считается законченным, когда выполняются одновременно:

1. **Воспроизводимость** — generated state можно проверить офлайн.
2. **Защита ownership** — обычный PR не может незаметно менять generated area.
3. **Наблюдаемость** — известны последняя попытка и последний success.
4. **Разделение публикации** — candidate не выдаётся за published.
5. **Устойчивость к ошибке** — failure не уничтожает last-known-good.
6. **Пользовательская доставка** — статус появляется до использования зависимой функции.
7. **Необязательность advisory** — сбой status channel не ломает основной runtime.
8. **Безопасная диагностика** — persistent status не содержит сырых секретов/trace.
9. **Документированная ручная операция** — есть одна каноническая команда полного запуска.
10. **Переносимость решения** — следующий подобный updater можно спроектировать по этому документу, а не по истории конкретного диалога.
