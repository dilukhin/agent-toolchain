# Политика владения установками и дублирующимися версиями ПО

## Цель

`opencode_setup` должен не только устанавливать инструменты, но и понимать, какой экземпляр реально запускается, каким менеджером он установлен и не существует ли параллельная установка того же ПО.

## Основное правило

Для каждого управляемого или проверяемого инструмента setup собирает инвентаризацию доступных экземпляров:

- путь к исполняемому файлу;
- фактическую версию, если её можно безопасно определить;
- предполагаемый или подтверждённый менеджер установки;
- является ли экземпляр активным (первым в `PATH`);
- есть ли другие экземпляры в `PATH` или известные менеджеру пакетов установки.

Дублирование всегда должно быть отражено в отчёте. Setup не удаляет и не переустанавливает конкурирующую установку автоматически.

## Классификация

1. **Один экземпляр** — нормальное состояние. Если менеджер известен, он считается владельцем обновления.
2. **Несколько экземпляров в `PATH`** — неоднозначная активная среда. Setup сообщает пути и версии и рекомендует оставить один владеющий менеджер, а остальные установки удалить или изолировать.
3. **Дополнительная установка обнаружена, но изолирована от `PATH`** — допустимое состояние. Setup сообщает о ней и рекомендует оставить как есть, если изоляция намеренная.
4. **Версии расходятся** — setup отдельно сообщает, какой экземпляр активен и какая версия будет реально запускаться.
5. **Менеджер неизвестен** — setup ничего не удаляет и рекомендует определить происхождение установки вручную.

## Рекомендации при дублировании

Приоритет рекомендации:

1. сохранить менеджер, которому принадлежит активный экземпляр, если это однозначно и установка исправна;
2. удалить затенённую установку через её собственный менеджер;
3. если вторая версия нужна специально — изолировать её от общего `PATH` и запускать явно;
4. не менять порядок `PATH` как единственный способ исправления, если две независимые глобальные установки остаются активными.

## OpenCode

### Проверенный механизм автообновления

Для OpenCode `v1.18.18` проверены официальные исходники `anomalyco/opencode`:

- `autoupdate: true` определяет метод установки (`npm`, `pnpm`, `bun`, `brew`, `scoop`, `choco` и др.) и для patch-обновления вызывает соответствующий менеджер;
- для Chocolatey используется `choco upgrade opencode --version=<target> -y`;
- для npm используется `npm install -g opencode-ai@<target>`;
- `autoupdate: "notify"` выдаёт событие о доступной версии и **не запускает обновление**.

Источники:

- `https://github.com/anomalyco/opencode/blob/v1.18.18/packages/opencode/src/cli/upgrade.ts`
- `https://github.com/anomalyco/opencode/blob/v1.18.18/packages/opencode/src/installation/index.ts`
- `https://opencode.ai/docs/ru/config/`

Документация содержит замечание, что режим `"notify"` якобы работает только при установке без package manager. Код `v1.18.18` этому замечанию не соответствует: ветка `"notify"` выполняется до запуска `Installation.upgrade()` и независимо от типа обнаруженного менеджера. Для `opencode_setup` источником поведения конкретной поддерживаемой версии считаются проверенные исходники.

### Почему несколько установок опасны даже при корректном autoupdate

Сам по себе встроенный auto-update не обязан конфликтовать с Chocolatey/npm: OpenCode пытается обновляться через обнаруженный менеджер. Риск появляется, если одновременно установлено несколько копий. Тогда определение метода установки может стать неоднозначным: активный executable и сведения package managers могут указывать на разные установки.

Поэтому `opencode_setup` использует политику:

- управляемое значение `autoupdate` — `"notify"`;
- OpenCode сам не изменяет installation;
- setup определяет активный экземпляр и владельца;
- при наличии нескольких активных глобальных установок setup не создаёт ещё одну и не обновляет произвольно выбранную копию;
- в отчёте показывается рекомендуемая команда обновления для обнаруженного владельца.

### Команды обновления

Если владелец однозначно определён:

- Chocolatey: `choco upgrade opencode -y`
- Scoop: `scoop update opencode`
- npm: `npm install -g opencode-ai@latest`
- pnpm: `pnpm install -g opencode-ai@latest`
- Bun: `bun install -g opencode-ai@latest`
- Homebrew tap: `brew upgrade anomalyco/tap/opencode`

Для неизвестного или неподдерживаемого менеджера setup не придумывает команду и просит использовать исходный способ установки.

## Расширение на остальные инструменты

Та же модель инвентаризации применяется к ключевому toolchain: OpenCode, Git, Python, Node.js/npm и `uv`. Для `ssh_relay`, `agent-safe`, `bundle` и `tunnelctl` она должна применяться при добавлении их stable launcher/deploy-механизма: setup обязан отличать управляемый экземпляр от другой глобальной или пользовательской установки.

## Безопасность

Инвентаризация read-only. Обнаружение дубля само по себе не даёт права выполнять uninstall, удалять каталоги, менять системный `PATH` или переписывать package-manager state. Такие действия допускаются только как отдельное осознанное решение пользователя.
