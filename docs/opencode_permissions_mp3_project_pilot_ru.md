# MP-3: project-scoped P0 на OpenCode 1.18.32

Статус: кодовый opt-in и disposable проверка; пользовательская машина ещё не измерена.

## Что меняется

`toolchainctl p0 enable --workspace /absolute/git/root` ставит native policy и P0 plugin в `<root>/.opencode`. Глобальный OpenCode config/plugin команда не меняет. Один pilot на одну локальную запись владения; повторный enable того же проекта и артефакта возвращает `changed=false`.

До изменения команда проверяет Linux, точный `opencode --version = 1.18.32`, закреплённый source bundle, фактическую конфигурацию через `opencode debug config` и отсутствие конкурирующих permission, agent override, plugin, legacy tools и перенаправляющих переменных окружения. Вывод resolved config может содержать секреты, поэтому команда его не печатает и не сохраняет. После установки существующий MP-1 reconciler повторно сверяет owned config/plugin/runtime и запись владения. Неизвестное состояние даёт conflict.

`status` и `disable` принимают тот же `--workspace`; `disable` использует локальный проверенный cache и запись первоначальной версии, поэтому снимает pilot даже после обновления OpenCode. Без `--workspace` они сохраняют прежнее чтение/откат исторической глобальной установки. Обычные `check/apply/update --apply` не включают P0.

## Временный пользовательский цикл

1. Обновить установленный agent-toolchain после принятия PR, убедиться, что `opencode --version` показывает `1.18.32`, выбрать один корень Git-проекта.
2. До включения выполнить обычный короткий набор задач и записать число видимых запросов на подтверждение. Сырые команды и секреты в отчёт не копировать.
3. Выполнить `toolchainctl p0 enable --workspace /absolute/git/root`, затем `toolchainctl p0 status --workspace /absolute/git/root`.
4. Повторить сопоставимые задачи: просмотр файлов, `glob`, `pwd`, `git status`, поиск `grep` по одному существующему несекретному файлу. Отдельно отметить ASK для остальных команд. Затем `toolchainctl p0 metrics`.
5. Выполнить `toolchainctl p0 disable --workspace /absolute/git/root` и проверить `status`. При конфликте не удалять файлы вручную: нужны owner evidence и диагностика без вывода содержимого команд.

Метрики `native_ask` и `classifier_allow` показывают ASK-path после включения: доля автоматического продолжения равна `classifier_allow/native_ask`, если `native_ask > 0`. `native_allow` и `native_deny` этим счётчиком не измеряются; число реально увиденных подтверждений до/после фиксируется отдельно. `binding_reject` и ошибки не считаются снижением запросов. Снимки агрегированы по процессу и могут быть перезаписаны при повторном PID.

P0 разрешает автоматически только узкий однострочный `grep` по одному несекретному файлу плюс явно заданные native правила. Расширение на trusted workspace и решение через более сильную модель остаются последующим этапом после измерения residual ASK.
