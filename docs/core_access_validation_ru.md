# Проверка доступности опубликованного core (#53)

Bootstrap проверяет опубликованный `core`, ownership marker и точное содержимое
созданного entrypoint. Затем запускает **этот entrypoint** с внутренним аргументом
`--bootstrap-access-check`. Запущенный `toolchainctl` повторно читает marker и
весь объявленный payload через существующий валидатор установленного core.
Ответ содержит абсолютный путь исполняемого core, полный fingerprint и признак
неповышенного контекста. Bootstrap сравнивает ответ с ожидаемым результатом.

Проверка локальная: не вызывает reconciliation, сеть, YC, установку инструментов,
миграцию state или изменение PATH. Python запускается с `-B`. Время ожидания —
30 секунд. `--version` и его формат не меняются; identity локальной поставки
по-прежнему меняется вместе с fingerprint.

## Права и результат

Успех bootstrap (`configured` / `up-to-date`, exit 0) выводится только после
успешной проверки. Она подтверждает доступ **текущего обычного пользователя**,
а не всех пользователей компьютера.

На Windows проверяется `TokenElevation` текущего процесса; на Linux — ненулевой
эффективный UID. Запуск под Administrator/root не доказывает доступ обычного
пользователя: после публикации bootstrap возвращает exit 2 и сообщает, что
проверку нужно завершить без повышения прав. Повторный bootstrap запускают от
предполагаемого пользователя с теми же `AGENT_TOOLCHAIN_DATA_DIR` и
`AGENT_TOOLCHAIN_BIN_DIR`, если использовались переопределения. При неизменных
данных повторная публикация не производится. Автоматического переключения
учётной записи, запроса пароля или понижения токена в production-коде нет.

При ошибке после публикации выводится `failed`, новые пути и предыдущий backup
сохраняются для диагностики; успешный итог установки не объявляется. Это не
атомарный rollback: уже опубликованные файлы могут остаться на диске.
`toolchainctl update --apply` при ошибке bootstrap не переходит к `apply`.
Предшествующий конфликт ownership по-прежнему блокирует замену core/entrypoint.
ACL автоматически не исправляются, неизвестные объекты не принимаются во владение.

## Почему изменено создание Windows staging

Предыдущий способ: `tempfile.mkdtemp()` → копирование → rename в `core`.
`mkdtemp` создаёт каталог с режимом `0700`. В Python 3.13+ на Windows этот режим
задаёт специальный ACL вместо обычного наследования; rename сохраняет ACL.
Это проверяется отдельным отрицательным сценарием на Python 3.13.

Теперь **новый** Windows staging создаётся через эксклюзивный `mkdir(0777)`
со случайным UUID. На Windows такой mode не назначает POSIX-права всем:
используется обычное наследование ACL родителя. Коллизия имени — ошибка, без
удаления существующего объекта. ACL уже существующих каталогов не меняется.
На Linux сохраняется `mkdtemp` и закрытый режим `0700`.

Это не доказывает происхождение ACL конкретного исторического инцидента DIMA-HP:
там не зафиксированы точная версия Python и полная цепочка создания каталога.

Источники платформенного контракта:
- [Python os.mkdir](https://docs.python.org/3/library/os.html#os.mkdir);
- [Python tempfile.mkdtemp](https://docs.python.org/3/library/tempfile.html#tempfile.mkdtemp);
- [Windows TokenElevation](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_information_class).

## Воспроизводимые проверки

`tests/run_core_access_windows.ps1` разрешён только на одноразовом Windows runner
GitHub Actions. Он создаёт временного обычного пользователя (не администратора)
и отдельный каталог; пароль не пишется в файлы, аргументы или журналы.

1. Родитель тестового каталога явно разрешает доступ тестовому пользователю.
2. Администратор публикует core старым способом. Тест проверяет protected ACL,
   чтение администратором и отказ запуска обычному пользователю.
3. Администратор публикует core новым способом. Наследование сохраняется,
   bootstrap честно возвращает неподтверждённый обычный доступ.
4. Новый процесс с учётными данными обычного пользователя подтверждает свой
   неповышенный токен, marker/payload и запуск entrypoint. Два повторных bootstrap
   и installed `check` не меняют файлы/mtime и не создают state/config/backups.
5. Отдельные отрицательные fixtures запрещают чтение core, marker, payload и
   entrypoint. Bootstrap завершается ошибкой и сохраняет заданный SDDL.

Это настоящий отдельный стандартный пользователь, а не чтение elevated-процессом
и не имитация результата AccessCheck. Сценарий точно того же SID с двумя UAC
токенами отдельно не проверяется. Тест не подключается к реальным устройствам.

Linux-регрессия запускает настоящий обычный процесс, проверяет установку,
повтор без записи и отказы доступа к тем же четырём объектам. При запуске тестов
в root-контейнере без разрешённого переключения UID этот один тест явно пропускается;
в обязательном Linux CI он выполняется от обычного пользователя.

Модульные тесты дополнительно проверяют ложный путь/fingerprint, elevated-ответ,
неправильную форму ответа, ошибку запуска/timeout, сохранение результата публикации
и запрет перехода к `update --apply` после ошибки bootstrap.
