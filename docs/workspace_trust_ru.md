# Реестр доверенных рабочих каталогов

Реализация [#45](https://github.com/dilukhin/agent-toolchain/issues/45) хранит явный
постоянный выбор пользователя для конкретного каталога и областей `build`, `test`,
`static_check`, `git_read`. Она не меняет текущие решения ALLOW/ASK/DENY.
Область доверия — вход для будущего отдельно проверенного правила разрешений,
а не разрешение произвольной команды.

## Команды

Сначала должно существовать штатное состояние с валидным `manifest.json`, созданное
обычным `toolchainctl apply`. Команды доверия сами не запускают настройку окружения
или перенос старого состояния. При неизвестном состоянии они сообщают конфликт.

Пример для Linux:

```bash
toolchainctl workspace-trust add /home/user/projects/example --scope build --scope test
toolchainctl workspace-trust list
toolchainctl workspace-trust update /home/user/projects/example --scope test
toolchainctl workspace-trust remove /home/user/projects/example
```

Пример для Windows:

```powershell
toolchainctl workspace-trust add 'C:\Users\user\Projects\example' --scope build --scope test
toolchainctl workspace-trust list
toolchainctl workspace-trust remove 'C:\Users\user\Projects\example'
```

Требуется абсолютный путь. Его исходное написание сохраняется точно: регистр,
Unicode, разделители и завершающий разделитель не приравниваются эвристически.
Для последующих команд используйте то же написание, которое показывает `list`.

| Команда | Поведение |
|---|---|
| `add` | Наблюдает существующий каталог и записывает выбранные области. Повтор с той же идентичностью и областями ничего не меняет |
| `update` | Явно заменяет весь набор областей существующей точной записи; не подтверждает заново заменённый каталог |
| `remove` | Удаляет записи с точным исходным написанием пути для текущей платформы, включая устаревшие/исчезнувшие каталоги; отсутствие записи — без изменений |
| `list` | Печатает весь проверенный реестр в JSON; отсутствующий реестр — пустой список; записи/каталоги не создаёт |

`add` с другими областями сообщает конфликт и предлагает `update`. Если объект
каталога изменился, новый явный `add` заменяет устаревшую запись для этого написания
пути. Подкаталоги и другие написания/ссылки не наследуют доверие автоматически.
Изменение файлов внутри того же каталога не требует повторного добавления.

Изменяющие команды печатают `configured` или `up-to-date`; ошибка — код 2 и
диагностика в stderr. Диагностическая версия core также остаётся в stderr.

## Хранение и отказ при неоднозначности

Путь: `<canonical agent-toolchain state>/workspace-trust.json`:

- Linux: `${XDG_STATE_HOME:-~/.local/state}/agent-toolchain/workspace-trust.json`;
- Windows: `%LOCALAPPDATA%\agent-toolchain\state\workspace-trust.json`.

Это существующий пользовательский раздел состояния toolchain. Реестр не записывается
внутрь доверяемого каталога; попытка доверить каталог, содержащий раздел состояния,
отклоняется. Манифест сохраняет своё назначение и не получает секретов или разрешений.

Формат — `workspace-trust-registry/v1`, записи — `workspace-trust-fact/v1` с полями
`trust_class=development`, `workspace` и `scopes`. Новых произвольных полей нет.
Точное дублирование записи или JSON-ключа, неизвестная схема/область, пустой набор,
повреждённый файл, неверный манифест, ссылка/reparse point либо необычный тип объекта
дают конфликт. Такие объекты не перезаписываются и не исправляются автоматически.

Запись выполняется под исключительной блокировкой соседним файлом:
чтение валидного состояния → полный временный файл в том же каталоге → flush/fsync
→ повторное чтение исходного реестра → атомарная замена → проверка записанного файла.
Параллельный штатный писатель получает конфликт. Обнаруженное внешнее изменение
сохраняется. Ошибка после замены не вызывает слепого отката. После аварийного
завершения может остаться `workspace-trust.json.lock`: автоматического удаления
чужой/оставшейся блокировки нет; сначала требуется выяснить состояние писателя.
При отсутствии изменений байты и время изменения реестра сохраняются.

## Идентичность и поставщик данных

`observe_workspace(absolute_path)` получает `platform`, точный `requested_root`,
`resolved_root` и `object_identity` вида `<platform>:dev=<st_dev>:ino=<st_ino>`.
Сверяются результаты до и после разрешения пути; недоступная/нулевая идентичность
отклоняется. Это базовая идентичность объекта файловой системы, не хеш содержимого
и не бессрочная защита от повторного использования номера объекта файловой системой.
На Windows `st_ino` соответствует файловому индексу, на Linux — inode:
[контракт Python os.stat](https://docs.python.org/3/library/os.html#os.stat_result).

```python
from setup_workspace_trust import WorkspaceTrustProvider, observe_workspace

# Создание в доверенном контексте установленного toolchain.
provider = WorkspaceTrustProvider()
fact = provider.lookup(observe_workspace(absolute_workspace_path))
```

Поставщик запоминает штатный путь при создании, не принимает аргумент пути реестра
и не использует `AGENT_TOOLCHAIN_STATE_DIR`. Эта существующая переменная остаётся
переопределением CLI для изолированных проверок; тесты поставщика подменяют внутреннее
разрешение пути, а не расширяют его публичный интерфейс.

Системные HOME/LOCALAPPDATA/XDG-настройки принадлежат доверенному контексту запуска.
Будущий адаптер не должен конструировать поставщика в окружении, полученном от
модели, или принимать готовый факт из аргументов команды. Это обязательная граница
будущей интеграции, а не свойство аутентификации произвольного процесса Python.

Каждый `lookup` заново наблюдает объект, читает и проверяет весь реестр и применяет
точное сравнение из потребительского контракта. Нет подбора по префиксу или ближайшему
родителю. Ошибка/неточное совпадение/устаревшая идентичность дают `None` без записи.
Старый объект наблюдения также не пройдёт после фактической замены каталога.

## Связь с opencode_permissions

Проверенный источник:
[`opencode_permissions@7922d612f244882aae3d843a64393b1363b593d9`](https://github.com/dilukhin/opencode_permissions/tree/7922d612f244882aae3d843a64393b1363b593d9).

- [Контракт поставщика и хранения](https://github.com/dilukhin/opencode_permissions/blob/7922d612f244882aae3d843a64393b1363b593d9/docs/trusted_workspace_producer_contract_ru.md).
- [Схема и точное сравнение](https://github.com/dilukhin/opencode_permissions/blob/7922d612f244882aae3d843a64393b1363b593d9/docs/trusted_workspace_fact_design_ru.md).
- `workspace_trust_contract.py` — неизменённая копия upstream `tools/workspace_trust.py`,
  Git blob `bd8ce9d1a09bce989a21b8684a412d0d14683555`. Тест сверяет этот хеш
  после нормализации окончания строк Git. Изменение контракта требует явной сверки
  с его владельцем; отдельной семантики сравнения в producer нет.

Ручная команда пользователя считается явным выбором. Вызов от модели должен быть
отдельной операцией `workspace_trust_change` с подтверждением пользователя; прямые
известные записи реестра должны быть запрещены управляемой политикой. Эти правила,
защита пути/окружения адаптера, пояснение постоянного эффекта в запросе подтверждения
и первый условный ALLOW — следующий отдельный этап `opencode_permissions`.
Текущий этап их не включает и не активирует автоматически.

Доверие постоянно до отзыва и ограничено перечисленными областями. Оно не отменяет
запреты на секреты, разрушительные, системные или привилегированные действия.
Защита от вредоносной программы того же пользователя/root не заявляется. Новых
служб, подписей, TTL, счётчиков поколений и общей базы разрешений не добавляется.

## Проверки

`tests/test_workspace_trust_registry.py`: явные операции и повтор без изменений;
точные Windows/Linux пути; замена каталога; повреждения, дубли и неизвестные поля;
блокировка другого процесса; ошибки записи и повторной проверки; сохранение
внешнего изменения; чтение без записи; отклонение ссылок и Windows junction;
установленная публичная команда без исходного каталога.

Общие Windows/Linux проверки сохраняют регрессии обычных `check/apply/update`,
доступ к core обычного пользователя, managed helpers, OpenCode/BMAD, MP-1/MP-2 и
RouterAI. Все изменяющие проверки работают во временных каталогах.
