# Инцидент: `bootstrap_core.py --help` опубликовал локальный core

- Статус: подтверждён; локальный core временно сохранён по решению владельца; исправление CLI не выполнено.
- Дата: 2026-11-22.
- Среда: DIMA-HP, Windows, обычный non-elevated пользователь.
- Компонент: `bootstrap_core.py`, installed `toolchainctl`.
- Рабочий checkout: `C:\Users\Dima\Projects\agent-toolchain\agent-toolchain`, HEAD `cc65027cb2bfaff03cd698c3a1361e9391582dce` с незакоммиченными изменениями миграции OpenCode 2.x.

## Наблюдение и масштаб

При подготовке миграции OpenCode агент выполнил из рабочего checkout:

```text
python -B bootstrap_core.py --help
```

Целью был read-only просмотр справки, но процесс завершился с кодом 0 **после публикации** локального core. Существенные строки вывода:

```text
configured        agent-toolchain core  C:\Users\Dima\AppData\Local\agent-toolchain\core
up-to-date        toolchainctl entrypoint  C:\Users\Dima\AppData\Local\agent-toolchain\bin\toolchainctl.cmd
info              previous managed core retained  C:\Users\Dima\AppData\Local\agent-toolchain\core.previous.20261122231128.5052
```

Последняя строка о command resolution предлагала `toolchainctl apply`; **он не запускался**. Независимый read-back:

- установленный `toolchainctl --version`: `0.1.0.local.a5d24d67` (до вызова `0.1.0.cc65027c`);
- новый marker `core/.agent-toolchain-managed-core.json`: fingerprint `a5d24d6747922b259f8ee512e1dd6b192b99f5718326535ec2baf4656dc1d232`, без `source_ref`;
- сохранённый предыдущий marker: fingerprint `6f9e31cd8131993637ff9d552ff96f47e2d64020ad7107caed9adc46d765ee2f`, `source_ref=cc65027cb2bfaff03cd698c3a1361e9391582dce`;
- `opencode --version` остаётся `1.19.5`, активный executable по-прежнему `C:\ProgramData\chocolatey\bin\opencode.exe`;
- repo-local `safe status` при первоначальном разборе: `blocked=false`, `records=2`, записи относились только к ранее согласованной изолированной npm-установке; отдельной safe-транзакции публикации core не было.

Полную побайтовую проверку сохранённого предыдущего дерева и проверку `toolchainctl check/apply` после публикации не выполняли. Изолированный OpenCode 2.3.2 находится вне общего PATH. Данных о затрагивании облака, YC или удалённых систем этой командой нет; исходник bootstrap публикует локальные файлы.

## Независимый причинный разбор

1. **Непосредственный механизм — отсутствие обработки argv.** В `bootstrap_core.py:479–512` функция `main()` не принимает и не проверяет аргументы. Даже `--help` попадает в `source_fingerprint()`, `_publish_core()`, `_publish_entrypoint()` и `_validate_published()`. Публикация внутри `_publish_core()` переносит прежний core в `core.previous.*`, затем размещает новый. Режима «справка/неизвестный параметр → отказ до записи» у этой точки входа нет.
2. **Почему выпуск стал локальным:** `_source_ref()` (`bootstrap_core.py:285–330`) доказывает Git ref лишь для чистого checkout с совпадающими payload-байтами. В данном checkout были незакоммиченные правки; при отсутствии внешнего ref функция вернула `None`, и новый marker не получил `source_ref`. Это штатный fail-open для локального bootstrap, но опасен при случайном запуске.
3. **Человеческий/агентский фактор:** агент предположил, что `--help` — безопасная диагностическая опция, не проверив реализацию до вызова. `--help` не должен считаться read-only на неизвестной утилите по одному лишь написанию. Незапланированная публикация произошла без подготовленного rollback/checkpoint именно потому, что вызов ошибочно классифицирован как чтение.
4. **Почему это важно даже без администратора:** core установлен в пользовательском LocalAppData. Non-elevated shell достаточно для замены *пользовательского* executable, который затем запускает `toolchainctl`; отсутствие UAC не было защитой. Exit code 0 и сообщение `configured` подтверждают успешное действие, но не заменяют согласование изменения.

Восстановление автоматически не предпринималось. Владелец согласился **временно сохранить** новый `0.1.0.local.a5d24d67` для дальнейшей диагностики. Сохранённый прежний каталог не удалять; `toolchainctl apply` до проверки совместимости V1/V2 не запускать.

## Корректирующие действия (выводы расследования)

1. Для mutating CLI сначала распознавать **весь** argv, и только затем вычислять fingerprint, получать lock, делать filesystem/network writes. Неподдерживаемый параметр — ненулевой exit и отсутствие side effects; для bootstrap желательно требовать явное действие вроде `install`, оценив изменение существующих wrapper’ов и документированных команд.
2. `--help`/`-h` должны завершаться с кодом 0 без установки, записи или попытки обращения к секретам; само наличие справки не даёт права считать неизвестные инструменты безопасными до проверки реализации.
3. Проверить реальное воздействие на установленный пользовательский core до следующего `apply`. Держать сохранённый предыдущий каталог как точку восстановления, не выполнять blind rollback поверх нового без отдельной preflight/WhatIf и подтверждения.
4. Regression suite: изолированные каталоги/временный HOME; snapshot байтов и состава файлов до/после `--help`, `-h`, неизвестного и лишнего positional-аргумента у Python и двух wrapper’ов; assert exit code и *нулевые вызовы* публикации; позитивный путь с явной операцией. PowerShell и Linux проверять раздельно; защищённые native скрипты тестировать только синтетически.
5. Агентская процедура: перед вызовом потенциально mutating утилиты читать contract и исходный entrypoint; не пробовать `--help` у bootstrap/installer в реальной среде, если он не доказан безопасным; для рискованных публикаций использовать заранее проверенные rollback и `safe`.

Дмитрий предложил: (1) жёсткий отказ на неизвестные параметры в `bootstrap_core.py`; (2) добавить `--help`; (3) проверить остальные утилиты и выделить те, которым требуется аналогичный strict mode. Независимый аудит выше подтверждает необходимость первых двух для данного инцидента и выявляет конкретные дополнительные точки входа для третьего. Порядок реализации и совместимость изменения старого no-argument bootstrap требуют отдельного решения и тестов.

## Границы этой записи

Этот документ фиксирует инцидент, read-only диагностику и аудит исходников. Он не меняет код bootstrap/wrapper’ов, не восстанавливает прежний core, не разрешает `toolchainctl apply`, не доказывает прохождение V2 end-to-end и не означает завершение миграции OpenCode. Состояние `safe status blocked=false` отражает только журнал safe: незапланированный bootstrap был запущен вне него.
