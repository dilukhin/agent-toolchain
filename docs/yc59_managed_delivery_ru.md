# YC59: управляемая поставка и фактическая приёмка

Этот путь использует уже выбранные учётные записи и отдельный интерактивный
вход владельца. Новые учётные записи, группы и широкие ACL не создаются и не
меняются. Пробники YC59-ACTOR/G3/G4 не повторяются. SID берутся из уже принятых
наблюдений; SessionId в команды не переносятся — текущие значения читает ОС.
Установленный guard и общий Python остаются на месте.

## Подготовка со стороны агента

После штатного обновления установленного ядра:

```powershell
toolchainctl self-update
toolchainctl yc-owner apply
```

`apply` выполняет подготовку точных библиотек клиента и пакета нативного запуска,
проверяет SHA-256, сохраняет журнал и предыдущие версии. Он не запускает владельца
под SID агента, не повышает права и не выдаёт согласия. Возвращённый локальный
пакет — данные; начальное доверие владелец проверяет по независимо опубликованному хешу.

## Действия владельца

В уже подготовленном отдельном сеансе владельца открыть системный Windows
PowerShell 5.1 с `-NoProfile`. Проверять **одни и те же прочитанные байты** и
исполнять их из памяти: проверка файла с последующим запуском изменяемого пути
оставляет окно подмены. Нативный код C# уже встроен в сценарий запуска, сторонний Python для
проверки не используется.

Источник закреплён за конкретным коммитом, его SHA-256 приведён ниже.
Каждый запуск выполнять в новом системном PowerShell:

```powershell
$yc59Bytes = ([Net.WebClient]::new()).DownloadData('https://raw.githubusercontent.com/dilukhin/agent-toolchain/d171995455dabdeae5d9db779c8c0fa970013b2a/native/yc_owner_release.ps1')
$yc59Expected = '6ffaf03f930dae1d40c7d775b74dac9a76113fb11451da14eb5c314427188065'
$yc59Hash = [Security.Cryptography.SHA256]::Create()
try { $yc59Actual = ([BitConverter]::ToString($yc59Hash.ComputeHash($yc59Bytes))).Replace('-','').ToLowerInvariant() }
finally { $yc59Hash.Dispose() }
if ($yc59Actual -cne $yc59Expected) { throw 'YC59: неверные байты выпуска' }
& ([scriptblock]::Create([Text.Encoding]::UTF8.GetString($yc59Bytes))) `
    -SeedBytes $yc59Bytes -Mode Prepare -AgentSid 'ПРИНЯТЫЙ_SID_АГЕНТА'
```

Сначала `Prepare`, затем тем же проверенным сценарием в новом PowerShell `Check`.
Каталог назначения вычисляется из профиля владельца, идентификатора компонента и хеша сценария.
Подготовка создаёт только новый закрытый выпуск: точные Python 3.14.2 и
YC 1.39.0, компонент, полный список файлов и журнал `prepared → complete`.
Частичный журнал вызывает отказ без автоматического ремонта. Предыдущий
каталог выпуска сохраняется. `Check` повторно проверяет реальные объекты,
ACL/владельцев, SHA, состав файлов и завершённость журнала.

Далее — тот же запуск с `-Mode Run`. До Python проверяются обычные отдельные
учётные записи, собственный интерактивный вход владельца через WTS и локальная
консоль. `runas` в сеансе агента не принимается. Нужна однократная проверка
назначенных прав агента администратором: обычному владельцу Windows не даёт
полного чтения LSA. Окно `Run` печатает точные SID, UUID и новый путь отчёта.
В новом системном PowerShell администратора загрузить тот же сценарий по тому же
внешнему хешу и вызвать:

```powershell
& ([scriptblock]::Create([Text.Encoding]::UTF8.GetString($yc59Bytes))) `
    -SeedBytes $yc59Bytes -Mode AuditAgent -AgentSid 'SID_ИЗ_RUN' `
    -OwnerSid 'SID_ИЗ_RUN' -Nonce 'UUID_ИЗ_RUN' -AuditPath 'НОВЫЙ_ПУТЬ_ИЗ_RUN'
```

Это только чтение групп/прав и запись защищённого отчёта для точного запроса,
без изменения пользователей, привилегий или существующих ACL. Отчёт не является
согласием на YC. Административная учётная запись агента отклоняется; обход,
демоция или создание другого аккаунта автоматически не выполняются.

После допуска владелец вводит IAM-токен скрыто и точные ID облака, каталога,
ВМ, диска и снимка. Токен не передаётся агенту, в параметры команд, журнал или
репозиторий. С момента выбора действует окно свежести 60 секунд.

## Один запрос чтения

Агент в своём прежнем сеансе запускает:

```powershell
toolchainctl yc-owner read --owner-sid 'ПРИНЯТЫЙ_SID_ВЛАДЕЛЬЦА'
```

Клиент находит канал по SID владельца и проверяет настоящий SID/SessionId/PID
сервера через ядро. PID и номера сеансов из старых отчётов не используются.
Он получает неподтверждённое описание, предлагает точную операцию и ждёт
решения. Подтвердить её можно только в отдельной консоли владельца точной
фразой с UUID запроса. Затем клиент один раз потребляет согласие; при потере
ответа потребление согласия не повторяется. Подмена поля `approved` или API `once` OpenCode
ничего не разрешает.

Владелец выполняет только три точных запроса get, общий срок 30 секунд, повторы отключены,
json-rest, выдача 64 КиБ/8 КиБ на шаг. Ответ появляется только после проверки
всех трёх объектов и их связей. Сторона владельца печатает собственную квитанцию
с идентификаторами компонента и запроса, хешем запроса, безопасной проекцией и SHA результата. Хеш должен
совпасть с хешем агента. Установленный выпуск подтверждается по стороне владельца,
не по одному сообщению недоверенного агента. Исходный вывод YC и данные доступа не пересылать.

Успех приёмки: точные опубликованные компонент и сценарий, успешный `Check`, настоящая
квитанция владельца и совпавший результат выбранного снимка. Снимок `READY`
не доказывает восстановление: `restore_verified=false` сохраняется. Завершение
владельца отменяет оставшиеся согласия; общий защищённый замок не допускает
двух активных владельцев, вся группа потомков завершается до освобождения файлов.

Если штатный код отказал, сохранить фиксированный код отказа и остановить
затронутый путь. Не исправлять установленные политику и обёртку вручную, не обходить guard,
не повторять потерянное потребление и не менять учётные записи попутно.
