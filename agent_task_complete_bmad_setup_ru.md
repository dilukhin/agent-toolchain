# Задача агенту: довести opencode_setup до воспроизводимой рабочей конфигурации

> Статус: выполнено в PR [#1](https://github.com/dilukhin/opencode_setup/pull/1). Этот файл сохранён как историческая постановка задачи; текущее гарантируемое поведение описано в `README.md`, `setup_instructions.md` и `SUMMARY.md`.

## Контекст

Репозиторий `opencode_setup` должен позволять воспроизводимо восстановить рабочее окружение OpenCode на новой Windows/Linux-машине.

Уже реализована базовая часть:

- установка OpenCode CLI;
- конфигурация RouterAI;
- внешний файл API-ключа;
- базовый `AGENTS.md`;
- `@opencode-ai/plugin@1.15.4`;
- Windows/Linux setup-скрипты.

При аудите выявлено, что документация описывает BMAD-скиллы как установленную часть окружения, но текущие setup-скрипты их фактически не восстанавливают. Нельзя предполагать, что `@opencode-ai/plugin` сам устанавливает BMAD. Это нужно доказать либо опровергнуть по реальному локальному окружению.

На локальном компьютере есть проекты, где BMAD уже используется. Их следует считать главным эмпирическим источником для восстановления фактической схемы установки.

## Главная цель

Определить, как BMAD реально установлен и используется в существующих локальных проектах, затем доработать `opencode_setup`, чтобы он мог безопасно и воспроизводимо восстановить этот набор скиллов на новой машине.

## Правила работы

1. Работай сначала локально и исследовательски. Не меняй рабочие проекты, используемые как примеры.
2. Не удаляй и не перезаписывай существующие пользовательские конфиги без необходимости.
3. Не раскрывай API-ключи, токены, пароли и другие секреты ни в выводе, ни в Git.
4. Не копируй в репозиторий секреты или машинно-зависимые данные.
5. Не сканируй `node_modules`, `.git`, кэши, логи и большие build-каталоги без отдельной причины.
6. Не утверждай происхождение BMAD-скиллов, пока оно не подтверждено содержимым файлов, package metadata, lock-файлами, install scripts либо историей проекта.
7. Существующий файл RouterAI `api-key.txt` должен сохраняться при повторной установке; setup не должен заменять его заглушкой.
8. Linux setup должен сохранять права `0600` на файл API-ключа.
9. По возможности делай установку идемпотентной: повторный запуск не должен ломать рабочую конфигурацию.
10. Все изменения должны быть минимальными, понятными и проверяемыми.

## Этап 1. Найти реальные примеры BMAD

Найди локальные проекты, в которых используются BMAD-скиллы. Начни с доступных пользовательских каталогов проектов и конфигурации OpenCode.

Ищи признаки:

- `.agents/skills/`;
- `skills/*/SKILL.md`;
- имена `bmad-*`;
- `BMAD`, `_bmad`, `.bmad*`;
- `AGENTS.md`;
- `opencode.json`, `opencode.jsonc`;
- `package.json`, lock-файлы;
- setup/install/bootstrap scripts;
- README/документы, объясняющие установку BMAD;
- symlink/junction/copy-механизмы, если используются.

Не ограничивайся именами из `config_data.json`: фактическое локальное состояние имеет приоритет.

Зафиксируй:

- где физически находятся BMAD-скиллы;
- глобальные они или project-local;
- какие каталоги OpenCode реально читает;
- сколько скиллов реально присутствует;
- их точные идентификаторы;
- есть ли версии/metadata;
- откуда они были получены;
- существует ли генератор/установщик;
- связаны ли они вообще с `@opencode-ai/plugin@1.15.4`.

## Этап 2. Сравнить с opencode_setup

Проверь минимум:

- `README.md`;
- `SUMMARY.md`;
- `setup_instructions.md`;
- `bootstrap_prompt.md`;
- `config_data.json`;
- `setup_windows.ps1`;
- `setup_linux.sh`.

Составь таблицу расхождений:

`утверждение/настройка -> фактическое локальное состояние -> состояние opencode_setup -> требуемая правка`.

Особенно проверь известные проблемы:

1. В документации одновременно фигурирует «42 BMAD-скилла», тогда как зафиксированный список содержит больше идентификаторов. Определи фактическое число и унифицируй документы.
2. Нельзя считать `npm install @opencode-ai/plugin` установкой BMAD без подтверждения.
3. `bootstrap_prompt.md` нужно проверить на исполняемость. В текущей версии замечены подозрительные строки вида `177:` / `138:` в Bash-фрагменте — выясни происхождение и исправь как обычный shell-код.
4. Списки моделей RouterAI в разных файлах расходятся: например, `config_data.json` содержит `z-ai/glm-5-turbo`, а setup-скрипты могут его не создавать. Определи эталон по текущей рабочей конфигурации и синхронизируй.
5. Проверь точные model IDs, особенно GPT/Codex, и не меняй их без подтверждения локальным рабочим конфигом или актуальным фактическим источником.
6. Проверь, действительно ли каталог `%USERPROFILE%\.agents` / `~/.agents` нужен глобально и где именно должны находиться BMAD skills.

## Этап 3. Спроектировать воспроизводимую установку BMAD

После исследования выбери минимальный воспроизводимый механизм.

Предпочтительный результат:

- источник BMAD определён явно;
- установка не зависит от случайно существующего рабочего проекта;
- setup можно запустить на чистой машине;
- версия/ревизия BMAD фиксируется либо иным образом обеспечивается воспроизводимость;
- install/update логика отделена от пользовательских секретов и памяти;
- существующие пользовательские файлы не уничтожаются без backup/явной политики.

Допустимые варианты после подтверждения фактами:

- установка из npm-пакета;
- установка из отдельного git-репозитория на зафиксированной ревизии;
- копирование versioned skill-файлов, если лицензия и происхождение это позволяют;
- отдельный installer, который получает BMAD из подтверждённого upstream.

Не выбирай способ только потому, что он проще: сначала установи фактическое происхождение текущего рабочего набора.

## Этап 4. Реализация

Доработай Windows и Linux сценарии симметрично, насколько это возможно.

Желательное разделение:

- базовая установка OpenCode/RouterAI;
- установка BMAD;
- опциональные helper tools (`ssh_relay`, `bundle`).

Если BMAD можно безопасно включить в основной setup — сделай это. Если лучше отдельным скриптом, создай, например:

- `install_bmad_windows.ps1`;
- `install_bmad_linux.sh`;

или один переносимый механизм, если он действительно удобнее.

Требования к BMAD installer:

- идемпотентность;
- понятный вывод действий;
- отсутствие секретов;
- проверка источника;
- создание требуемых каталогов;
- корректная обработка уже существующих skills;
- отсутствие тихого уничтожения пользовательских модификаций;
- после установки — машинная проверка списка ожидаемых skills.

Если существующие пользовательские skills могут конфликтовать, сначала сравни содержимое/хэши и выбери безопасную политику: preserve / backup / update только управляемых BMAD-файлов.

## Этап 5. Исправить документацию

После реализации синхронизируй все документы с фактическим поведением.

В частности:

- одно точное число BMAD-скиллов, если фиксированный набор действительно является частью установки;
- точный источник и версия BMAD;
- что именно ставит `@opencode-ai/plugin`, а что нет;
- глобальные/project-local пути;
- Windows/Linux команды;
- поведение повторного запуска;
- optional helper tools;
- где пользователь должен вручную добавить RouterAI API key;
- что проверяет post-install validation.

`SUMMARY.md` можно сохранить как исторический документ, но исторические утверждения должны быть явно отделены от текущего гарантируемого поведения setup.

## Этап 6. Проверки

Не ограничивайся чтением кода.

Выполни безопасные проверки, доступные локально:

1. Syntax/parsing check PowerShell script.
2. `bash -n` для Bash scripts, если Bash/WSL доступен.
3. JSON parse для `config_data.json`.
4. Проверка generated `opencode.jsonc` хотя бы структурно.
5. Проверка того, что повторный запуск не заменяет существующий `api-key.txt`.
6. Проверка BMAD install в безопасном временном HOME/USERPROFILE либо другом изолированном target, если архитектура скриптов это позволяет.
7. Сравнение фактически установленных BMAD IDs с эталонным списком.
8. Проверка отсутствия секретов в diff.
9. Проверка, что installer не зависит от конкретного username или абсолютного локального пути разработчика.

Не выполняй destructive test на реальном рабочем пользовательском окружении, если можно проверить во временной директории.

## Этап 7. Git

Перед изменениями проверь состояние репозитория и не затри чужую незавершённую работу.

Сделай изменения в отдельной рабочей ветке, например:

`fix/reproducible-bmad-setup`

Коммиты разделяй логически, например:

- `fix: make base setup idempotent`
- `feat: add reproducible BMAD installation`
- `docs: align setup documentation with verified configuration`
- `test: add setup validation checks`

Не push/merge, если текущая политика окружения требует отдельного подтверждения; в таком случае подготовь локальные коммиты и отчёт.

## Критерии приёмки

Работа считается выполненной, когда:

1. Установлено фактическое происхождение BMAD в существующем рабочем окружении.
2. Определён реальный список и число используемых BMAD-скиллов.
3. Нет ложного утверждения, что `@opencode-ai/plugin` устанавливает BMAD, если это не доказано.
4. На чистом target можно воспроизвести BMAD без ручного копирования из случайного проекта.
5. Windows/Linux установка документирована и по возможности автоматизирована.
6. Повторный запуск setup не уничтожает RouterAI API key.
7. Linux API key имеет `0600`.
8. `bootstrap_prompt.md` не содержит повреждённых команд и соответствует реальной схеме установки.
9. README, setup instructions, config data и scripts не противоречат друг другу по BMAD и ключевым моделям.
10. Есть validation/check, который обнаруживает неполную установку.
11. В Git diff нет секретов и машинно-зависимых пользовательских данных.
12. Сформирован итоговый отчёт с доказательствами и перечнем проверок.

## Формат итогового отчёта

Верни краткий, но фактический отчёт:

### Найдено
- реальные BMAD paths;
- источник/версия;
- число и список skills либо ссылка на generated manifest;
- связь или отсутствие связи с `@opencode-ai/plugin`.

### Изменено
- файлы;
- что изменено в каждом;
- политика обновления существующих skills.

### Проверено
- конкретные команды/тесты;
- PASS/FAIL;
- что не удалось проверить и почему.

### Git
- ветка;
- commit SHA;
- рабочее дерево clean/dirty;

### Осталось
- только реальные незакрытые вопросы, если они есть.

Главный принцип: сначала восстановить фактическую рабочую схему по локальным примерам, затем автоматизировать её. Не подгонять локальное окружение под текущие предположения документации.
