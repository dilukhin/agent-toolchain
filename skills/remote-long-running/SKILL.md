# Remote long-running

Используй этот skill перед сборками, CMake build, CTest, интеграционными/нагрузочными тестами, длительными скриптами и другими процессами, которые могут работать дольше обычного transport timeout.

## Основной контракт

- Таймаут транспорта не означает завершение процесса.
- Не запускай вторую копию операции, пока не установлена судьба первой.
- Для удалённых длительных процессов через `ssh_relay` используй `job`, а не `exec`/`sudo-exec`.
- Контролируй задачу через `job status` и ограниченный `job tail`; не выкачивай полный журнал без причины.
- Финальный результат определяет exit code, а не факт старта и не локальный timeout ожидания.
- Живой PID вместе с новым прогрессом означает, что операция продолжает работать.
- Строки вида `[ 71%] Building CXX object ...` являются явным признаком прогресса.
- Тишина в журнале сама по себе не доказывает зависание.
- При подозрении на зависание проверь PID, CPU и дочерние процессы до решения об остановке или повторном запуске.
- После ошибки не повторяй идентичную команду без анализа причины.

## Работа через ssh_relay

Для удалённой длительной задачи:

```text
py ssh_relay.py job start --name <session> --job <job> "<command>"
py ssh_relay.py job status --name <session> --job <job>
py ssh_relay.py job tail --name <session> --job <job> --lines <N>
py ssh_relay.py job wait --name <session> --job <job> --timeout <seconds>
```

Если `job start` или управляющий транспорт завершились неоднозначно, сначала выполни `job status`/`job list` для того же имени job. Не запускай команду повторно до выяснения состояния.

## Большие передачи файлов

Большой upload/download — не long-running job. Используй специализированный механизм передачи `ssh_relay` (`upload`/`download`) и его ограничения/таймауты. Не оборачивай крупную передачу в `job` только ради увеличения времени ожидания.
